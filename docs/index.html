CSC 466 · David Mooers

Fixed and Adaptive Input Timeouts for a Phone-Controlled Multiplayer Game

Proposal Logbook Project updates Project report Demo and presentation

Proposal

In a shared-screen game with phone controllers, a gap in input updates can make the host keep moving a player after they release a control. A timeout that expires too soon can also stop movement while the player is still holding the control. Can an adaptive timeout balance those two errors better than a fixed timeout?

The plan is to build a Unity game with a PC host and phone-browser controllers that send input periodically over WebSockets using Unity Transport. Both policies will use the same transport and message format. The fixed policy expires input after a configured interval. The adaptive policy estimates a timeout from recent arrival intervals and their variation, with minimum and maximum limits.

Related work

AirConsole is a reference for the shared-screen setup, and TCP’s retransmission timer is an example of using measured timing to set a timeout.

My RS4 paper is Real-time latency prediction for cloud gaming applications by Doriana Monaco et al., published in Computer Networks in 2025. The authors use recent network measurements to forecast latency and trigger game-state prediction when delays are expected to get too high. That relates to my project because I’m also using recent timing to make a game decision: when the host should stop applying the last controller input.

Logbook

Picking a project idea

October 2026

I wanted to try using phones as controllers for a game on a shared screen. The part I wanted to figure out was what happens when the host stops hearing from a controller. How long should it keep moving the player based on the last input?

I decided to keep the game simple. I’d use Unity on the PC, run the phone controller in a browser, and send input over WebSockets. That way I could try both timeout settings without changing how the controller sends input.

Writing the proposal

October 2026

While writing the proposal, I narrowed down what to measure. The player can keep moving after letting go, or stop moving while they’re still holding the control. I looked at AirConsole for the phone controller setup and at TCP’s retransmission timer for ideas on using recent message timing.

My plan was to get a fixed timeout working first, add logging, then try a timeout that adjusts as messages come in. I wanted to see how both behaved at different send rates and with delays. Read the proposal.

I’ve since switched my RS4 paper to Monaco et al.’s cloud gaming study. It’s a closer fit for the question I’m testing about delayed input in games.

Fixed-timeout prototype

October 27, 2026

I got a cube moving in Unity from a WASD controller over WebSockets. The controller keeps sending even when I hold the same key. I added a P shortcut so I could pause the sends while keeping the connection open. The host writes arrivals and timeouts to a CSV.

I ran the host and controller on the same computer at 30 Hz with a 500 ms timeout. The host got 436 messages. Between pauses, messages arrived about 33.38 ms apart on average, with a standard deviation of 4.40 ms. I paused seven times. The cube stopped each time and could move again when I resumed sending. The host detected the timeout at an average input age of 502.75 ms.

Next I wanted to add the adaptive timeout and script the holds and releases so I could repeat the same test. I still hadn’t tried a phone controller or separate players.

Adaptive timeout in Unity Play Mode

November 11, 2026

I added the adaptive timeout and tested both modes in Unity Play Mode. I used a script to hold and release movement and pause the controller at the same points in each run. The host got 206 messages per mode over localhost WebSockets, with the controller set to 30 Hz.

When I paused sending at release, the cube stopped after 519.5 ms on average with the fixed timeout and 100.0 ms with adaptive. I also paused briefly while the input was still held. Adaptive stopped the cube in all three trials, and fixed kept it moving.

Adaptive was at its 80 ms minimum every time it timed out. Next I want to try a fixed 80 ms setting too, then run the test with phone controls on a separate device and vary the network delay.
